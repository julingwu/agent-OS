# 受控发布验证版（2026-10-31）

这一版先建立可靠的单执行主体，再保留红绿两轨的验证、发布入口。
不会把正在运行的 Python 任务、审批或设备连接强行迁移到另一进程。

## 使用

1. 双击 `program/Verify.cmd`，执行回归和真实进程验证。
2. 使用 根目录的 `Start.cmd` 启动，在浏览器访问 `http://127.0.0.1:8077/ui/`。
   所有后台由该入口统一管理。
3. 如需本机文件、命令、截图能力，无需另开脚本，Start 会自动启动本机执行程序。
   首次从旧版升级时，应重启旧的本机 daemon；新默认值为显式 `local` 模式。
   已配对的真实设备令牌继续有效，错误或已吊销的令牌不再降级成其他设备。
4. 前端、静态资源已构建到 `ui_dist/`。这次交付以浏览器为验证入口；没有重新打包桌面 EXE/APK。

如 8077 已被旧服务占用，新启动器会明确报错，不会把旧实例当作新版本。
请先结束旧服务再启动。启动脚本不会自动杀占用端口的其他进程。

## 修复、验证、发布流程

```text
Agent 在主轨执行修复并完成相应测试/前端构建
  → POST /v1/supervisor/restart_standby
  → 备用轨导入工具模块、检查数据库、记录候选代码指纹
  → POST /v1/supervisor/switch
  → HTTP 202：排队，不表示已经切换
  → 网关暂停新任务准入，停止主轨调度器
  → 等待当前任务、工具、审批、后台进程及请求结束
  → 结束旧执行主体，将候选轨作为唯一执行主体启动
  → 验证身份、角色、数据库访问和代码指纹
  → 更新路由，关闭旧连接，客户端和设备重连
  → completed；失败则尝试恢复原轨，明确报告恢复结果
```

Agent 提交发布后必须结束本轮回答，不能在同一轮循环等待 `completed`。
因为网关正等待这一轮结束，两者互相等待会导致发布一直停留在 draining。
这一规则已加入 Agent 系统提示词。

备用轨不运行初始化迁移、任务恢复、调度器或业务请求。
任一时刻仅有一个执行主体。两轨不能同时消费同一个会话。

## 如何判断结果

查看顶部发布面板，或请求 `GET /v1/supervisor/status`。

| release.phase | 含义 |
| --- | --- |
| queued | 请求已持久保存，尚未切换 |
| draining | 等待现有任务结束；仍由原轨执行 |
| promoting | 当前工作已结束，正在启动新执行主体；业务请求短暂返回 503 |
| completed | 新轨已通过检查并接管请求 |
| rolled_back | 新轨发布失败，原轨重新启动成功；不是恢复旧代码版本 |
| failed | 发布或原轨恢复失败，查看错误和后端日志 |

`release.busy` 列出等待的会话数、运行进程数、挂起工具/审批数和后台线程。
运行期间允许停止现有任务、停止后台进程、处理本地工具审批。
未知的应用线程也会阻止发布，不会为了切换强杀仍在工作的进程。
需要长期运行的后台服务应由外部服务管理器托管，否则需要先结束它才能发布。

重复提交同一轮发布会返回当前操作，不会再次翻转主备。
发布期间不能重启备用轨。代码在验证后发生变化时，不能继续使用旧验证结果。
网关重启会把未完成发布标为失败，启动记录中的主轨；必须重新验证候选版本。

发布记录：`data/supervisor-release.json`。
后端日志：`logs/backend-8081.log`、`logs/backend-8082.log`。
状态接口提供的 ready 是身份和基础就绪检查，不代表真实模型、业务验收或所有工具已通过。

## 本次修复范围

- 切换前必须验证备用轨，健康或身份检查失败时不会切流。
- 发布是独立网关中的持久操作，不依赖原 Agent 线程继续轮询。
- 排空后再重启执行主体，避免请求、任务、事件流和设备归属分裂。
- 状态查询与发布串行，返回独立快照，避免“旧主轨 + 新阶段”的混合响应。
- 单边 WebSocket 结束时取消另一边的转发，并关闭下游连接。
- 备用轨不清理主轨任务，不重复启动定时任务。
- 执行中的追加消息作为转向消费，避免每次追加都排一个重复回合；收尾时到达的消息仍会被接续处理。
- 停止接口和界面只报告停止请求，不提前伪造任务结束。
- 唯一执行主体重启时，将上代未闭合的 turn 标为 interrupted，保留记录，不自动重放可能已有副作用的工具。
- 补齐网页解析及 Word/Excel/PDF 工具所需的 Python 依赖。
- 明确设备身份：显式本机模式可用，错误真实令牌不再静默降级；更新旧 8 KiB 事件测试至现行 128 KiB 协议。

## 可复现验证

以下命令在 `program/` 目录执行。日常操作只需根目录 `Start.cmd`，详见 [启动说明](START.md)。

```powershell
..\.venv\Scripts\python.exe -m pytest tests/test_controlled_release.py -q
..\.venv\Scripts\python.exe -X utf8 scripts\verify_controlled_release.py
```

真实进程验证使用临时数据库、临时工作区、随机本机端口和临时确定性模型。
会实际启动网关、两个后端和一个受管后台进程，建立消息流及设备 WebSocket。
测试模型会在真实 Agent 回合内部请求发布并结束任务，由网关完成切换。
验证绿→红、红→绿两向发布，以及切换后的设备重连和历史消息读取。
不请求真实模型，不修改生产库，不重启现有生产服务；退出时回收测试进程。
成功结果写入 `outputs/controlled-release-verification.json`。

还包含故障测试：不健康候选、验证后代码变化、重复切换、繁忙执行主体、发布失败、
原轨恢复失败、私有管理端点、备用轨无恢复副作用、并发状态查询，以及晚到消息接续。

## 当前边界

这是带短暂维护窗口的受控发布，不是零停机任务迁移。
两轨仍从同一代码目录启动，尚无独立不可变版本目录、数据库迁移回退或旧代码快照。
恢复原轨只代表重新启动原轨；如果磁盘上的改动使两个轨道都无法启动，会明确失败，不能承诺自动恢复旧版本。
因此应先完成测试再发布；涉及数据库结构、网关本身或依赖升级的改动，需要单独维护窗口。
运行中的 supervisor.py 不会因切换后端自动加载新代码，需要正常重启网关。

真实模型生成的修复质量尚需人工业务验收；确定性模型验证的是执行与发布控制链。
