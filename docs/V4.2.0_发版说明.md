# AgentOS V4.2.0 发版说明 · 意图分类、工具预算、复合流

发布日：2026-10-20 ｜ 基线：`main@97d45ef`（V4.1.0）

## 一句话

派单不再靠关键词猜：一次轻量模型调用判断意图，认不准就先问用户；检索在底座上被限次，模型想「再搜一次」会被系统中断；开发 + 分析的复合需求会自动串成一条流。

## 三大战役

| 战役 | 变更 | 位置 |
|---|---|---|
| 一 · LLM 意图分类 | 关键词不再决定流程。每次派单调用**一次**轻量模型（temp 0，`max_tokens=120`，提示词约 200 token），输出 `{task_type, confidence, reason, secondary}`；`confidence < 0.6` 时**不建项目、不拉人**，只在会话里追问「请问您是需要一份报告，还是开发一个小工具？」 | `app/flows.py::classify/plan`、`app/ui/dispatcher.py` |
| 二 · 工具预算 | 底座硬限制：单次 Run 搜索 ≤ **5** 次、抓取网页 ≤ **3** 次（`M0_MAX_SEARCH_CALLS` / `M0_MAX_FETCH_CALLS`）。超限立即 cancel 本轮，run 记 `tool_cap_exceeded`，界面诊断显示「网络检索次数超限，请基于已有资料生成报告」；同时把上限写进 prompt、并把流程阶段预算独立为 `M0_FLOW_STAGE_BUDGET`（默认 40k） | `app/engine/runner_acp.py`、`app/pipeline.py::_flow_execute` |
| 三 · 自适应角色（复合流） | 模型可返回第二类（`secondary`）。software + analysis 这类需求自动组合成「软件交付流 + 分析报告流」：先开发后分析，副流程节点前缀 `an_` 防撞车，建群时两组角色一起拉 | `app/flows.py::_compose_nodes`、`dispatcher.open_group` |

## 验收记录（真机）

| 断言 | 结果 |
|---|---|
| 「帮我瞧瞧今天金子啥情况」→ analysis | 真模型返回 `analysis / 0.95 / "询问金价行情，属于行情数据研判类需求"`；流程 `FLOW-ANALYSIS`，阶段 `retrieve → analyze → author → review → deliver`；群成员：研究员(research)、金融分析师(data)、审计/合规(audit) |
| 低置信度追问 | 测试覆盖：0.42 置信度 → 返回 `clarify=True`、项目数为 0、会话里出现追问文案 |
| 一次派单只调一次模型 | 测试断言调用次数 = 1、`max_tokens ≤ 150`、提示词 < 1200 字符 |
| 工具上限 | 单测：第 6 次 `web_search` 返回「网络检索次数超限（5 次）…」；第 4 次 `web_fetch` 返回抓取超限；`pwsh` 等非网络工具不计数；上限可由环境变量收紧 |
| 复合流 | 「开发一个黄金监控并分析的系统」→ `FLOW-SOFTWARE+FLOW-ANALYSIS`，13 个节点（先 8 段软件 + 5 段分析，交付放最后），群里同时出现 dev 与 data |

## 已知边界

1. 意图分类是**一次**模型调用，模型不可用（无 key / 网络断）时退回离线词表（`M0_INTENT_LLM=0` 也可强制），此时「金子/瞧瞧」这类口语靠词表兜底，长尾说法仍可能认错。
2. 「紧急」类需求有硬覆盖（线上故障/宕机/止血等词直接走紧急流），不依赖模型判类。
3. 工具上限按**工具名包含匹配**计数（search/搜索/检索、fetch/url/抓取）；模型若用别的名字抓网页，可能绕过计数——底座仍受流程阶段预算 40k 兜底。
4. 复合流是「串行两段」而非真并行 DAG；拆子项目尚未实现。
5. 低置信追问只有一轮：用户回答后需要再发一次需求，系统再分类一次。

V4.2.0 为功能冻结版本：此后只接受缺陷修复。
